# Design: A tested tool that moves a sellbird.db into the Postgres backend

## Context

See the phase assessment (`.kbd-orchestrator/phases/postgres-gke-deployment/assessment.md`) and plan (change 5). Operator decisions D1–D12 and the plan-stage decisions (restated goals adopted, single tenant with RLS deferred, production overlay in the platform repository) apply.

## Decisions

Add `sellbird storage move --from <sqlite> --to <postgres-dsn>` that copies every table in dependency order inside one transaction, preserves ids, timestamps, JSON and signal confirmation state, refuses a non-empty target, and reports per-table row counts. Exercised only with fixture databases; moving the operator's real data is excluded.

### How it is built

- **Command.** `sellbird storage move --from data/sellbird.db --to-env SELLBIRD_DATABASE_URL` (`sellbird/storage_postgres/move.py`, registered as a fourth action of the existing `storage` command in `sellbird/storage_postgres/cli.py`). The target is named by an environment variable, never on the command line, and its connection string is never printed; errors go through the backend's `translate_error`, which drops values and DSNs. Run it as the runtime role `sellbird_app` (it reads and writes rows and advances the rowid sequences; it needs no DDL), after `sellbird storage migrate` and before Sellbird is started against the database.
- **Source.** Opened read-only (`mode=ro` URI) and read from one snapshot (`BEGIN` held for the whole read). It must be on the newest SQLite schema (`PRAGMA user_version == len(state.MIGRATIONS)`); an older file is refused with "run `sellbird status` once", a newer one with "use the release that made it". Its tables must be exactly the known set, so a table the move would leave behind stops it.
- **Target checks, before any write.** `MAX(schema_version.version) == EXPECTED_SCHEMA_VERSION`; the target's tables (from `pg_catalog`, not `information_schema`, so privileges don't hide columns) equal the known set, each with a `bigint GENERATED BY DEFAULT` `rowid`; column sets equal per table on both sides; column types are only text, bigint and double precision; every foreign key points at a table copied earlier.
- **One transaction.** `BEGIN`; `SET LOCAL statement_timeout = '15min'` and `lock_timeout = '10s'` (a running Sellbird makes the move stop, not hang); `LOCK TABLE ... IN EXCLUSIVE MODE` on all 18 tables (readers allowed, writers held off); any table with a row raises `TargetNotEmpty` listing the tables, and the rollback writes nothing. Then each table, in the order `signal_codes` first and `observations` after it, is streamed from SQLite in batches into `COPY ... FROM STDIN` with its `rowid` (SQLite insertion order and gaps kept), read back through a server-side cursor in `rowid` order, and compared with what was sent (count and checksum); any difference raises and rolls back. Finally each identity is set to `MAX(rowid) + 1` (`setval(..., false)`, 1 for an empty table), then `COMMIT`.
- **Values.** Text, including ISO timestamps and JSON, is copied byte for byte; NULL stays NULL; integers and floats keep their type. SQLite's loose typing is coerced only where it is lossless (a number in a text column becomes its text, an integral float or numeric text in a bigint column an int, a number or numeric text in a double column a float); anything else, a NUL in text or a blob, stops the move naming `table.column (rowid N)`, never the value.
- **Checksum** (`move.Checksum`). Per table: SHA-256 over UTF-8 lines, first the JSON array of the column names (rowid included) sorted, then for each row in rowid order the JSON array of its values in that column order, compact separators, `ensure_ascii=False`, NULL as `null`, ints as ints, floats by `repr`. Equal checksums mean equal contents and value types. The command prints rows and `sha256:<hex>` per table and a total.
- **Not in scope.** Moving the operator's real `data/sellbird.db` (excluded by the plan); Postgres to SQLite; merging into a non-empty target.

### Deviation: how the expected checksums are recorded

`tests/fixtures/move/expected.json` records, by hand from the builder's deterministic data, each table's row count, its rowids and its full rows. A SHA-256 digest can't be computed by hand, and under VLBV nothing generated runs before the boundary, so the file doesn't hold literal digest strings. `tests/test_storage_move.py` computes each expected checksum from those recorded rows with its own implementation of the definition above (independent of the tool's code) and compares it with: the tool's report after moving the fixture into an empty Postgres; the rows read back from Postgres; and the fixture SQLite file itself (`move.sqlite_checksums`, no Postgres needed). Read-back rows are also compared value for value with the recorded rows.

## Verification

Implemented in its plan round and verified once at the phase boundary (VLBV). Scenarios and negative controls are defined in the plan's coverage table and the adopted contract. Baseline test files changed by this change must be listed here with a justification so the boundary's source-digest check can accept them.

New test files (none of them baseline):

- `tests/fixtures/move/build_fixture.py`: the fictional fixture (example.test businesses, generic invented people, 555-01xx numbers): 18 tables, 32 rows, rowid gaps, three signal states and a signal time series, three outbox states, address and domain suppressions, empty tables, non-ASCII text, NULLs, irregular JSON spacing.
- `tests/fixtures/move/expected.json`: the recorded counts, rowids and rows.
- `tests/test_storage_move.py`: everywhere: the records agree with themselves and with the builder, the fixture's SQLite counts and checksums equal the recorded values, two builds are identical, the tool's checksum follows the written definition, refusals decided from the source (missing file, not SQLite, older schema, unknown table) and the source is never changed, CLI registration. With the Postgres DSNs: counts and checksums equal the recorded values after a move into an empty database (scenario "Counts and checksums match"); rows read back exactly; the app sees the same confirmed signals; new rows follow the moved rowids; a target holding one settings row is refused and every table is unchanged (scenario "Existing data is protected"); a target one schema version behind is refused; the CLI prints counts and checksums but never the connection string or its password.

Postgres cases need `SELLBIRD_TEST_PG_MIGRATE_DSN` and `SELLBIRD_TEST_PG_APP_DSN` (as in `tests/storage_contract/backends.py`) and `pip install -e '.[postgres,dev]'`. Unset, they skip with that reason; set, a missing psycopg fails rather than skips.

Changed baseline test files (justified): none.

## Risks

- Real names: no real person's or business's name, email, phone, address or domain in code, tests, docs or commits; use fictional example.com / example.test data.
- Secrets: credentials only through operator-created Secrets or an uncommitted local .env.
- Strict values: a real database whose SQLite cells hold something that can't become the Postgres column type losslessly (for example `''` in an integer column) is refused, naming the cell's table, column and rowid. That is deliberate (no silent change), but it can block a move until the cell is fixed.
- Large databases: the move is one transaction bounded by a 15-minute statement timeout per COPY; a database too large for that needs the timeout raised. Lock waits are bounded at 10 s.
- Started too early: if Sellbird ran against the target before the move (seeding the signal catalog), the target is no longer empty and the move is refused; re-create the database, migrate, then move.
- New tables: a future migration that adds a table must add it to `move.TABLES` (in dependency order) and the fixture; until then the move refuses, by design, because the table sets differ.
